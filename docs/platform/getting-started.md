# Genie server — запуск и эксплуатация

Архитектура и решения — [[platform/vision]], [[platform/backend]]; автоматизации — [[platform/automations]]; знания — [[platform/knowledge-vault]]; как провести пилот с командой — [[platform/pilot]].

Запуск в контейнере — [[platform/docker]].

## Что это

Один процесс `genie serve` на машине команды:

- веб-интерфейс и API (задачи, эпики, доска, команды, документация, автоматизации, уведомления);
- запуск агентов «ходами» (оркестратор, команды, разовые задания) через pi или любой харнесс с shell;
- движок автоматизаций и встроенные уведомления;
- каналы: Telegram (long polling, публичный адрес не нужен) и почта (SMTP);
- хранилище знаний — Obsidian-совместимый vault (git-репозиторий).

Данные лежат в каталоге данных (`--data`, `$GENIE_DATA` или `~/.local/share/genie`):

```
server.db            пользователи, проекты, автоматизации, запуски, уведомления, очередь доставки
projects/<slug>/     трекер проекта (genie.db) — если проект не зарегистрирован на месте
vault/               хранилище знаний (git), открывается в Obsidian
vault-index.db       поисковый индекс vault (кэш, можно удалить)
sessions/, runtime/  сессии и журналы ходов агентов
workspaces/          рабочие каталоги агентов для проектов без кода
config.json          настройки (необязательно)
```

## Сборка и первый запуск

Нужны Rust (stable), Node 23.6+ (для веба и pi) и git.

```bash
cargo build --release -p genie          # бинарь target/release/genie
npm install && npm run build:web        # веб-интерфейс web/dist

./target/release/genie project add shop --name "Магазин" --repo ~/code/shop   # проект с кодом
./target/release/genie project add product --name "Продукт"                    # проект без кода
./target/release/genie serve --web web/dist                                    # http://127.0.0.1:7420
```

Пока на сервере нет пользователей, веб открыт без входа — но только с этой машины (loopback). Репозиторий, где уже есть `.genie/`, подключается со всеми задачами на месте: TS-инструменты продолжают работать с тем же файлом.

Всё это можно сделать и в вебе: сервер без проектов предлагает создать первый, а на странице «Проект и люди» в локальном режиме — учётную запись администратора (после неё вход обязателен для всех).

## Люди

```bash
echo 'пароль-не-короче-8' | genie user add anna --name "Анна" --admin --password-stdin
genie project invite shop --role member  # ссылка-приглашение: человек сам выбирает логин и пароль
genie project member shop pm member      # роль в проекте: viewer, member, admin, owner
genie user token anna                    # личный токен для командной строки, MCP-клиентов и скриптов
```

После появления первого пользователя вход обязателен для всех. Роли: viewer — только чтение, member — задачи и знания, admin — автоматизации, участники, релизы, owner — всё. Администратор сервера — владелец всех проектов.

В вебе:

- **«Проект и люди»** — название проекта, оркестратор (автономность), интеграция по умолчанию; участники и их роли; ссылки-приглашения с ролью (ссылка одноразовая, живёт 7 дней). Меняют администраторы проекта, остальные видят.
- **«Сервер»** (только администраторы сервера) — проекты и новый проект, учётные записи: права администратора, отключение (отключённый не может войти, его сессии и токены перестают работать), новая учётная запись.

У задачи может быть **ответственный** — человек проекта, который отвечает за неё наравне с командой агентов. Его назначают в карточке задачи (поле «Ответственный») или оркестратор (`genie task update --assignee <login>`); назначенный получает уведомление. Когда агент переводит задачу в «Нужно решение», вопрос приходит ответственному и автору задачи (если ответственного нет — автору и администраторам проекта). Задачи, за которые вы отвечаете, собраны в разделе «Мои задачи» (`G` `M`).

Чтобы позвать человека, упомяните его в комментарии к задаче: `@login`. Упоминание доходит до участников проекта — в веб, Telegram или почту, как настроено в профиле; так же людей зовут агенты.

Доступ из локальной сети или tailnet: `"bind": "0.0.0.0"` и имена в `"allowHosts"` (проверка заголовка Host защищает от DNS rebinding), `"publicUrl"` — адрес для ссылок в письмах и Telegram.

## Командная строка

Всё, что люди и агенты делают в genie, есть и в командной строке: `genie <объект> <действие>`. Объекты — `task`, `team`, `mail`, `docs`, `job`, `automation`, `agents`, `project`, `user`, `me`, `server`; `genie <объект> --help` показывает действия, `genie <объект> <действие> --help` — их аргументы.

```bash
genie task list --status review          # задачи на ревью; ls — то же, что list
genie task show G-7
genie task create "Экспорт в CSV" -a "файл скачивается"
genie team board                         # все агенты: состояние, текущий шаг, почта
genie docs search "экспорт"
genie me questions                       # вопросы, которые агенты задали вам
genie me answer 12 1=XLSX 2=Бухгалтерия
genie automation runs
genie agents check                       # файлы ролей, шаблонов, навыков и MCP
```

- **Куда идёт команда.** С `GENIE_TOKEN` — на сервер `GENIE_URL` от имени владельца токена (`genie user token <login>`; права проверяет сервер). Без токена — прямо в каталог данных как оператор сервера (администратор), запущен сервер или нет: так работают первый пользователь и проект.
- **Проект** — `--project shop` или `GENIE_PROJECT`; без него — первый ваш проект. Названный проект недоступен — ошибка, а не другой проект.
- **`--json`** печатает ответ API как есть — для скриптов.
- Отчёты (`genie agents check`, `genie server doctor`) печатаются целиком и завершаются ненулевым кодом, если нашли проблемы.
- Агенты пользуются той же командной строкой: у каждого свой токен, а в промпте — таблица команд, разрешённых его роли. Прежние `genie agent show`, `genie agent send`… работают как псевдонимы (`genie agent show` = `genie task show`).

## Свой агент: MCP-сервер genie

Тот же каталог операций сервер отдаёт как MCP-сервер `http://<сервер>/mcp` (Streamable HTTP). Подключите его к своему агенту — Claude Code, pi (с pi-mcp-adapter), Codex… — и ведите задачи, команды агентов, знания и сервер словами.

```bash
genie user token anna        # или в вебе: «Профиль» → «Токен для CLI и MCP»
claude mcp add --transport http genie http://127.0.0.1:7420/mcp --header "Authorization: Bearer <токен>"
```

Другие клиенты — в их конфигурации MCP:

```json
{ "mcpServers": { "genie": { "url": "http://127.0.0.1:7420/mcp", "headers": { "Authorization": "Bearer <токен>" } } } }
```

- Инструмент на группу: `genie_task`, `genie_team`, `genie_mail`, `genie_docs`, `genie_job`, `genie_automation`, `genie_agents`, `genie_project`, `genie_user`, `genie_me`, `genie_server`. Действие выбирает `action`, аргументы каждого действия перечислены в описании инструмента, ответ — тот же текст, что печатает командная строка.
- Кто вызывает, решает токен: человек видит то, что делают люди (администраторы — и администрирование), агент genie — команды из таблицы своего промпта. Права проверяет сервер — так же, как для командной строки и веба.
- Проект — аргумент `project` любого инструмента, заголовок `X-Genie-Project` или адрес `…/mcp?project=shop`; по умолчанию — ваш первый проект.
- На машине сервера без пользователей токен не нужен, но клиент должен слать заголовок `X-Genie: 1` — защита от запросов со страниц в браузере.

## Агенты

Участники команд и оркестратор работают **живыми сессиями**: по долгоживущему процессу `pi --mode rpc` на агента с расширением genie-bus. Почта доходит до занятого агента между его шагами, свободного — сразу, прерывание (`interrupt`) останавливает текущий шаг. Подробно — [[platform/agent-bus]]. Разовые задания автоматизаций запускаются ходами (`pi --print`).

Модели ролей — `roleModels` (как в `config/default.json`). Агенты действуют через командную строку `genie` с токеном, который сервер выдаёт сессии или ходу; переменная `GENIE_ROLE=off` не даёт TS-расширению genie для pi вмешаться.

```json
{
  "roleModels": { "executor": { "model": "openai-codex/gpt-6-luna", "thinking": "high" } },
  "runtime": {
    "mode": "auto",
    "maxSessions": 12,
    "idleStopSecs": 900,
    "turnTimeoutSecs": 1800,
    "maxAttempts": 3,
    "askTimeoutSecs": 180
  }
}
```

`sessionCommand` (как запускается сессия) и `command` (как запускается ход) — списки групп аргументов; группа пропускается, если её подстановка пустая. Навыки, MCP и правила роли приходят через подстановки `{skill}` (группа повторяется для каждого каталога навыков), `{?limitSkills}` (`?` — группа остаётся, только если значение задано, сама подстановка ничего не добавляет), `{guard}` и `{mcpConfig}`: заменяя команду pi, сохраните эти группы. Другой харнесс подключается заменой `command` и `"mode": "turns"`: ему нужно принять промпт роли и сообщение хода и уметь выполнять shell-команды.

Автономность проекта:

- `autonomous` — оркестратор сам берёт задачи в работу и сам их закрывает;
- `assisted` — работает так же, но закрывает задачи человек: готовую задачу оркестратор переводит в «Нужно решение» с итогом и тем, что проверить, а закрыть её сам сервер ему не даст (рекомендуется для пилота);
- `manual` — серверный оркестратор не запускается (например, если оркестратором работает ваша сессия pi).

Интеграция по умолчанию — как результат задачи попадает в основную ветку, если в самой задаче не договорились иначе (например, «владелец смотрит ветку genie/<задача> и сливает её в main»). Оркестратор берёт её без вопросов, команда получает её вместе с задачей. Обе настройки меняются в вебе на странице «Проект и люди» или через `PATCH /api/projects/<slug>` (`{"autonomy": "assisted", "integration": "…"}`). `genie serve --no-agents` запускает сервер без агентов.

### Песочница агентов

Каждый агент (участник команды, оркестратор, разовое задание) запускается в песочнице [bubblewrap](https://github.com/containers/bubblewrap), если она работает на машине:

- вся система видна агенту только для чтения;
- писать он может в свой рабочий каталог и git-репозиторий за ним (коммиты worktree), в файлы своих сессий, в каталог pi (`~/.pi` или `PI_CODING_AGENT_DIR`), в свой `/tmp` и в кэши инструментов (`~/.cache`, `~/.npm`, `~/.cargo`, `~/.rustup`, `~/go`, `~/.m2`, `~/.gradle`…);
- каталога данных сервера (базы, `config.json` с токенами Telegram и SMTP, vault) агент не видит — только свои промпт, правила и навыки;
- не видит он и другие проекты с их worktree, файлы трекеров, ключи и учётные данные из домашнего каталога (`~/.ssh`, `~/.gnupg`, `~/.aws`, `~/.kube`, `~/.docker`, `~/.config/gh`, `~/.netrc`…) и сокеты сессии рабочего стола;
- у агента свой `/proc`: процессы машины и окружение сервера (секреты MCP-подключений) ему не видны;
- сеть общая: модели и API genie агенту доступны.

Установка: `sudo apt install bubblewrap`. На Ubuntu 24.04 и новее непривилегированные пространства имён ограничены AppArmor; если `genie agents check` пишет, что песочница не работает, разрешите их (`sudo sysctl kernel.apparmor_restrict_unprivileged_userns=0`) или добавьте профиль AppArmor для `bwrap`.

```json
{ "runtime": { "sandbox": { "mode": "auto", "writable": ["~/.local/share/uv"], "hidden": ["~/Documents"] } } }
```

- `mode`: `auto` — песочница, если bubblewrap работает, иначе агенты запускаются без неё (сервер предупреждает в журнале и в `genie agents check`); `bwrap` — без песочницы агенты не запускаются; `off` — выключить.
- `writable` — ещё пути, куда агентам можно писать (например, кэш инструмента, которого нет в списке); `hidden` — ещё пути, которые агентам видеть нельзя. `~/` — домашний каталог пользователя сервера.
- Держите pi и node вне репозиториев проектов: чужой проект скрыт вместе со всем, что в нём лежит.
- Подключение MCP с `"gateway": false` работает внутри песочницы; если его сервер хранит состояние в домашнем каталоге, добавьте этот путь в `writable`.
- Запреты роли `files: read` и `denyCommands` по-прежнему соблюдает защитное расширение (мягко): рабочий каталог агента в песочнице доступен на запись, чтобы ревьюер мог собрать и прогнать тесты.

## Роли и шаблоны команд

genie поставляется со встроенными ролями (`analyst`, `executor`, `reviewer`, `tester`, `documenter`, `researcher`, `orchestrator`) и пресетами команд (`standard`, `pair`, `full`, `abap`, `spike`, `research`). Администратор сервера настраивает их под свой контекст в вебе («Команда и правила» → «Агенты») или файлами в каталоге данных; сервер подхватывает изменения без перезапуска. Остальные видят роли и шаблоны на той же странице и собирают по ним команды: кнопка «Собрать команду» в карточке задачи. Устройство и решения — [[platform/agent-roles-and-teams]].

```
<data>/agents/<id>.md        роль: настройки во frontmatter, промпт в теле
<data>/teams/<id>.json       шаблон команды
<data>/skills/<имя>/SKILL.md навык
<data>/mcp.json              MCP-подключения (формат mcpServers)
```

Новая роль берёт за основу класс процесса (`base`) и меняет его разрешения:

```markdown
---
title: QA
description: Tests the change and ticks the acceptance criteria it verified.
base: tester
allow: [task.check]
projects: [shop]
---
You are the QA engineer of a focus team…
```

Файл с идентификатором встроенной роли её переопределяет: незаданные поля и промпт (при пустом теле) остаются встроенными. Например, `<data>/agents/executor.md` из одного frontmatter с `model: …` и `instructions: …` меняет исполнителю модель и дописывает правила.

Шаблон — участники и связи между ними: `handoff` (передаёт работу), `returns` (возвращает на доработку), `reports` (докладывает оркестратору), `consults` (можно спрашивать). Связь с `on: <статус>` исполняет сам genie: когда задача входит в статус, адресат получает письмо. С `"mail": "flow"` участники пишут только по связям: сервер отказывает письмам вне маршрута, оркестратору без `reports` можно слать только вопросы и блокеры. На экране команды сверху — схема: граф с живым состоянием участников (кто работает, кто кого ждёт, какие передачи впереди); «Свернуть схему» оставляет от неё строку «кто чем занят» (на телефоне схема свёрнута сразу).

```json
{
  "title": "QA pair",
  "description": "An executor and a QA engineer for small changes.",
  "stage": "delivery",
  "workspace": "worktree",
  "members": [{ "role": "executor" }, { "role": "qa" }],
  "relations": [
    { "from": "executor", "to": "qa", "type": "handoff", "on": "review", "note": "ready to test" },
    { "from": "qa", "to": "executor", "type": "returns", "on": "changes_requested" },
    { "from": "qa", "to": "orchestrator", "type": "reports", "note": "the test verdict" }
  ]
}
```

- Проверка: `genie agents check` печатает ошибки и предупреждения (код выхода 1 при ошибках), `genie agents ls` — роли и шаблоны, как их видит сервер. Сломанный файл не останавливает работу: действует его последняя валидная версия.
- Из командной строки — как на странице «Агенты»: `genie agents show role:security-reviewer` (файл, где используется, проблемы, хеш), `genie agents save role:security-reviewer --file security-reviewer.md --base-hash <хеш>` (сервер сначала проверяет файл и не сохранит сломанный или изменённый кем-то после вас), `genie agents delete`, `genie agents history`, `genie agents preview <шаблон> --task G-7` — что получит каждый участник; то же для `team:<id>`, `skill:<имя>` (и его файлов `skill:<имя>/<путь>`) и `mcp`; `genie agents mcp-check <подключение>` и `genie agents mcp-calls` — проверка подключения и журнал вызовов.
- Разрешения ролей проверяет сервер: `status.refine`, `status.start`, `status.rework`, `status.submit`, `status.approve`, `status.return`, `task.scope`, `task.plan`, `task.check`, `task.create`, `task.block`, `docs.read`, `docs.write`, `mail.team`, `mail.orchestrator`, `team.peek`. Отзыв разрешения действует сразу; промпт и модель — со следующего старта сессии агента.
- Навыки, MCP-подключения и запреты роль получает в харнессе при старте агента:

  ```markdown
  ---
  title: Ревьюер безопасности
  base: reviewer
  skills: [owasp-review]
  mcp: [semgrep, "github:get_*"]
  denyCommands: ["git push*", "git reset --hard*"]
  ---
  ```

  - `skills` — только эти навыки из `<data>/skills` и `skills.paths` и навыки репозитория (`.agents/skills`, `.pi/skills`). Роль без поля `skills` получает навыки, установленные для pi, и навыки репозитория.
  - `mcp` — подключения из `<data>/mcp.json`: `сервер` целиком или `сервер:шаблон` для отдельных инструментов. Нужен pi-mcp-adapter (`pi install npm:pi-mcp-adapter`). Агенты ходят в MCP через шлюз genie: в конфиге агента только адрес шлюза и его токен, сервер сам запускает MCP-сервер (или ходит к нему по HTTP) с секретами из своего окружения, показывает агенту только выданные инструменты и пишет каждый вызов в журнал проекта — его видно на вкладке «Агенты → MCP», там же кнопка «Проверить». Переменные, на которые ссылается `mcp.json` (`${env:…}`), держите в окружении сервера: агентам они не передаются. Глобальных MCP-конфигов пользователя и репозитория агент не видит, а устанавливать серверы сам не может. Без адаптера агенты работают без MCP, и `genie agents check` предупреждает об этом. Если адаптер подключён нестандартно, задайте `"runtime": { "mcpAdapter": true }`.
  - Подключение, которое должен открывать сам харнесс (например, со входом через OAuth в браузере), помечается `"gateway": false`: агент получает его запись с подставленными секретами, а вызовы не попадают в журнал. `"runtime": { "mcpGateway": false }` выключает шлюз для всех подключений.
  - `denyCommands` — шаблоны shell-команд (`*` — любой текст), их блокирует защитное расширение genie; `files: read` убирает инструменты записи. Это мягкие ограничения: через shell агент может их обойти.
  - Отзыв (новый запрет, закрытое подключение, `files: read`) действует на работающего агента со следующего вызова инструмента. Новые навыки и подключения — со следующего старта его сессии.
- API: `GET /api/agent-config` — каталог проекта; `GET/PUT/DELETE /api/roles/<id>`, `/api/templates/<id>`, `/api/skills/<имя>` (и его файлы — `/api/skills/<имя>/files/<путь>`), `GET/PUT /api/mcp`, `POST /api/mcp/<id>/check`, `GET /api/mcp/calls`; `POST /api/templates/<id>/preview` — что получит каждый участник; `GET /api/agent-config/history` — журнал правок. Менять может только администратор сервера; сохранение проверяет файл и сверяет `baseHash` с версией, с которой начиналась правка.
- Оркестратор видит каталог в своём промпте и собирает команды через `genie team spawn <задача> --template <id>` или `--member <роль>[:<модель>]`, добавляет участника — `genie team add-member <команда> <роль>`, список — `genie team templates` и `genie team roles`. Автоматизации принимают любую роль (`agent.role`) и шаблон (`team.template`).

## Telegram и почта

```json
{
  "publicUrl": "http://genie.local:7420",
  "telegram": { "token": "123456:ABC…" },
  "smtp": { "host": "smtp.example.com", "port": 587, "username": "genie", "password": "…", "from": "genie <genie@example.com>", "security": "starttls" }
}
```

- Telegram: человек в профиле жмёт «Привязать Telegram» и отправляет боту `/start КОД`. Дальше в чат приходят уведомления и вопросы агентов; ответить — кнопкой варианта или reply на вопрос. `/new текст` — новая задача во входящие.
- Почта: уведомления и вопросы со ссылкой на страницу ответа. Для локальной проверки подойдёт Mailpit (`"security": "none"`, порт 1025).
- Доставка идёт через очередь с повторами (до 8 попыток с нарастающей паузой); дубли отсекаются.

## Автоматизации

В вебе: «Автоматизации» → «Плейбуки» → «Добавить». Готовые правила:

- «Задача закрыта → знания, чейнджлог и уведомление» — документатор обновляет страницы пространства проекта (по политике раздела — прямо или предложением), запись в `changelog.md`, сообщение автору задачи и админам;
- «Новая задача от человека → аналитик → вопросы автору» — вопросы уходят автору в Telegram или почту, ответы попадают в задачу и будят оркестратора;
- «Решение не принято за сутки → напоминание».

Свои правила — JSON в редакторе правил, формат в [[platform/automations]].

## Знания

Хранилище — `<data>/vault` (или `vault.path`), git-репозиторий: открывайте его в Obsidian. Пространство каждого проекта создаётся автоматически, с `changelog.md`. Политики публикации и владельцы разделов — в `vault/.genie/vault.json` (или `PUT /api/docs/spaces/<name>`); по умолчанию люди пишут сразу, агенты — предложениями на ревью («Предложения» в вебе). Перенести существующие `docs/`: `genie vault import ~/code/shop/docs --space shop`.

### Obsidian у каждого: синхронизация с git

Чтобы люди работали с базой знаний в своём Obsidian, дайте ей удалённый git-репозиторий (пустой или с уже существующим хранилищем команды):

```json
{ "vault": { "remote": "git@git.example.com:team/knowledge.git", "branch": "main", "syncSecs": 120 } }
```

- Сервер каждые `syncSecs` секунд забирает правки из репозитория, сливает их со своими и отправляет свои (правки из веба и от агентов — коммиты от имени автора). Доступ к репозиторию — у пользователя сервера: SSH-ключ в `~/.ssh` (агентам он не виден) или токен в адресе.
- Каждый участник клонирует репозиторий и открывает папку как хранилище Obsidian; правки уходят в git — плагином Obsidian Git или вручную.
- Правки разных строк сливаются сами. Если одни и те же строки изменили и в репозитории, и на сервере, на странице остаётся версия сервера, а версия из репозитория ложится рядом — `<страница>.conflict-<время>.md`; страница, удалённая в одном месте и изменённая в другом, остаётся изменённой. Владельцы раздела и администраторы получают уведомление — сведите версии и удалите копию.
- Личные файлы Obsidian (открытые вкладки `workspace.json`, кэш, корзина) в репозиторий не попадают: сервер ведёт `.gitignore`; общие настройки `.obsidian/` — по желанию команды.
- Состояние и «Синхронизировать сейчас» — на странице «Сервер»; `genie vault sync` — один раз из терминала (для остановленного сервера); `genie doctor` проверяет, что репозиторий отвечает.

## Надёжность

- **Резервная копия** на ходу: `genie backup /backups --keep 14` — консистентные снимки всех баз (`VACUUM INTO`), `git bundle` хранилища и конфигурация сервера (`config.json` с секретами каналов, роли, шаблоны, навыки, `mcp.json`) в `/backups/genie-<время>/` с правами 0700; `--keep` оставляет столько последних копий. Ежедневно — `genie-backup.timer` (ниже).
- **Восстановление**: остановите сервер; `server.db` и `projects/<slug>.db` из копии положите на место (трекер проекта — `genie.db` в его каталоге: `genie project list` покажет путь), vault — `git clone vault.bundle vault`, конфигурацию — из `config/`; запустите сервер и `genie doctor`.
- **Рестарт** безопасен: прерванные ходы агентов возвращают свои письма и повторяются, запущенные задания возвращаются в очередь, шаги автоматизаций продолжаются с места остановки, события журнала обрабатываются ровно один раз на правило.
- **Сбой агента**: прогон повторяется с нарастающей паузой, упавшая сессия перезапускается с тем же разговором; после `maxAttempts` подряд участник переходит в `error`, оркестратор получает письмо, письма участника сохраняются до `genie team restart`. Зависший шаг прерывается, о возможном цикле сообщается оркестратору.
- **Индекс знаний** — кэш: `genie vault reindex`.
- Журналы: ходы — `<data>/runtime/<project>/<agent>/turn-<id>.log`, сессии — журнал действий в истории ходов и `stderr.log` рядом; `genie team board` и `GET /api/agents` — состояние всех агентов и задержки доставки, `genie team turns` — последние ходы и их ошибки; в вебе — история запусков автоматизаций по шагам.

## Готовность сервера: `genie doctor`

`genie doctor` (запускайте от пользователя сервера, с теми же `GENIE_DATA` и `PATH`) проверяет всё, без чего пилот не пойдёт, и называет, что сделать:

- каталог данных (запись, свободное место), собранный веб (`--web`);
- люди (есть ли администратор) и проекты (трекер открывается, репозиторий на месте);
- агенты: ошибки конфигурации ролей, `pi` в `PATH`, **модели ролей доступны pi** (по `pi --list-models`: нет входа у провайдера или опечатка в id — ошибка), pi-mcp-adapter для прямых MCP-подключений;
- песочница bubblewrap, git и имя для коммитов (без него агенты коммитят как `<имя>@genie.local`);
- Telegram и почта (сервер SMTP отвечает), `bind`, `allowHosts` и `publicUrl` (ссылки в сообщениях открываются).

Код выхода ненулевой, если есть проблемы. Та же проверка — на странице «Сервер» в вебе («Готовность»).

## Как идёт работа: `genie stats`

`genie stats [--days 7] [--project shop] [--json]` — что произошло за период по каждому проекту: задачи (создано, людьми, готово, отменено, открыто сейчас), время от создания до готовности (медиана и 90%), сколько раз агенты спрашивали людей и как быстро люди отвечали (до первого слова человека в задаче), возвраты с ревью, комментарии людей и агентов, запуски агентов и сбои, вызовы MCP, предложения в базу знаний, кто из людей работал. То же — «Как идёт работа» на странице «Сервер» (неделя или месяц) и `GET /api/stats?days=7`.

## Как служба (systemd)

```bash
cargo build --release -p genie && npm ci && npm run build:web
sudo deploy/install.sh        # /opt/genie/bin/genie, /opt/genie/web, пользователь genie, /var/lib/genie, /var/backups/genie
sudo -iu genie npm install -g --prefix ~/.local @earendil-works/pi-coding-agent
sudo -iu genie pi             # /login у провайдеров моделей ролей
sudo cp deploy/systemd/genie.service deploy/systemd/genie-backup.service deploy/systemd/genie-backup.timer /etc/systemd/system/
sudo systemctl daemon-reload && sudo systemctl enable --now genie genie-backup.timer
sudo -iu genie env GENIE_DATA=/var/lib/genie /opt/genie/bin/genie doctor --web /opt/genie/web
```

- `genie.service` — сервер от пользователя `genie` (`HOME` — там логины pi), данные в `/var/lib/genie`, перезапуск при сбое; агенты — процессы службы и останавливаются вместе с ней, после перезапуска работа продолжается.
- Секреты MCP-подключений (`${env:NAME}` в `mcp.json`) — в `/etc/genie/secrets.env`: они остаются у сервера и не попадают агентам.
- `genie-backup.timer` — копия каждый день в 03:30 в `/var/backups/genie`, 14 последних. Копируйте этот каталог и на другую машину.
- Журнал сервера — `journalctl -u genie -f`.
