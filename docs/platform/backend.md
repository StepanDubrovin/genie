# Бэкенд genie на Go — стек, границы и перенос

Контекст — [[platform/vision]], решения — [[platform/decisions]] (PD8, PP1–PP5).

## Зачем переносить сейчас

- **Сервер становится единственным владельцем данных.** Сегодня каждый процесс (pi-участник, CLI, веб) пишет в SQLite сам, и права ролей проверяются в каждом клиенте. Когда пишет только сервер, журнал событий, авторизация, аудит и жёсткие права агентов появляются в одном месте.
- **Один статический бинарь** — самое простое развёртывание на локальной машине сейчас и самый простой контейнер потом.
- **Сейчас это дешевле всего.** Доменная логика — около 6,3 тыс. строк TypeScript: трекер ≈1,4 тыс., команды и почта ≈1,4 тыс., docs ≈2 тыс., веб-сервер ≈0,9 тыс., CLI ≈0,6 тыс. Поведение закреплено 118 тестами (≈3,3 тыс. строк). Всё, что до переноса было бы написано на TS (журнал, пользователи, автоматизации, каналы), пришлось бы переносить второй раз.

## Go или Rust

| Критерий | Go | Rust |
|---|---|---|
| Характер работы genie: HTTP, SSE, SQLite, запуск и надзор процессов, боты, почта, git | Родная территория: горутины, стандартная библиотека покрывает HTTP, JSON, SMTP, процессы | Справляется так же, но через async (tokio) — больше сложности на том же объёме |
| Скорость изменений, пока домен ещё меняется | Высокая: простой язык, быстрые сборка и тесты | Ниже: модель владения, долгая компиляция, дорогой рефакторинг |
| Код, который пишут агенты genie | Короткий цикл «правка → сборка → тест», мало итераций на ошибки компиляции | Больше итераций на borrow checker и lifetimes, ревью сложнее |
| Надёжность типов | Хорошая, но есть `nil` и нет исчерпывающих enum | Лучше: sum-типы, исчерпывающий `match`, нет null |
| Производительность | С большим запасом для команды | С ещё большим запасом — genie он не нужен |
| Развёртывание | Статический бинарь без cgo, кросс-компиляция одной командой | Статический бинарь (musl), сборка сложнее |
| MCP SDK | Официальный `github.com/modelcontextprotocol/go-sdk` | Официальный `rmcp` |
| SQLite с FTS5 | Pure-Go драйвер без cgo (проверено спайком) | `rusqlite` со встроенным SQLite |
| Порог входа для людей | Низкий | Высокий |

**Рекомендация — Go.** genie — это в основном связующий слой: API, процессы, интеграции, события. Его выгоднее быстро менять, чем выжимать из него производительность. Rust может понадобиться позже для отдельных компонентов, где он действительно выигрывает (например, изолированный раннер-песочница); с сервером они будут общаться по тем же протоколам.

**Спайк, 2026-09-28.** `modernc.org/sqlite` v1.59 (SQLite 3.53.4), сборка с `CGO_ENABLED=0`: работают WAL, `busy_timeout`, FTS5 с токенайзером `unicode61 remove_diacritics 2`, `bm25()` и `snippet()` — всё, на чём держится нынешний поиск docs. Статический бинарь спайка — 9,6 МБ. Официальный MCP SDK для Go доступен (v1.8.0).

## Что на чём

| Часть | Технология | Судьба |
|---|---|---|
| Сервер: проекты, задачи, события, команды, почта, автоматизации, каналы, знания, API, MCP | Go | Новый код; логика переносится из `src/tracker`, `src/team`, `src/docs`, `src/web`, `src/notify.ts` |
| CLI `genie` | Go, тот же бинарь | Переносится из `src/cli/genie.ts`, работает через API сервера |
| Веб-интерфейс | React + TypeScript (Vite) | Остаётся; сборка встраивается в бинарь (`go:embed`) |
| Расширение pi | TypeScript | Остаётся тонким клиентом: инструменты ходят в сервер; остаются отрисовка в TUI, живая карточка команды, доставка почты в сессию и защитные проверки харнесса |
| Промпты ролей, шаблоны команд | Markdown, JSON | Без изменений: `agents/*.md`, формат `config/default.json` |
| Харнесс агентов | pi (Node) | Внешняя зависимость рядом с сервером; на этапе контейнеров — в одном образе |

## Устройство сервера

```
cmd/genie/                 main: `genie serve` и команды CLI
internal/store/            SQLite: соединения, миграции, транзакции
internal/tracker/          проекты, задачи, эпики, стейт-машина, права ролей, DoR/DoD, артефакты
internal/events/           журнал, курсоры подписчиков, SSE-поток
internal/team/             команды, участники, почта, дайджест, имена
internal/runtime/          запуск агентов (pi: herdr или headless rpc), пульс, восстановление
internal/orchestrator/     серверный оркестратор: пробуждение, аренда, автономность
internal/knowledge/        vault: парсер, индекс FTS5, ссылки, L0/L1-контекст, запись, ревью, синхронизация
internal/automations/      правила, запуски, шаги, опросники
internal/channels/         telegram, email
internal/auth/             пользователи, сессии, токены, права проекта
internal/api/              REST + SSE для веба
internal/mcp/              MCP и HTTP для агентов
web/                       SPA (как сейчас)
integrations/pi/           расширение pi (переезжает из src/extension)
```

Зависимостей — минимум: `net/http` из стандартной библиотеки (маршруты по шаблонам), `modernc.org/sqlite`, `modelcontextprotocol/go-sdk`, `robfig/cron`, `emersion/go-imap` и `wneessen/go-mail` для почты. Telegram Bot API — прямыми HTTP-вызовами или тонкой библиотекой. Git — через CLI `git`, как сейчас: `git worktree` библиотека go-git не покрывает.

## Контракты

1. **Веб: REST + SSE.** На время переноса сервер повторяет текущие маршруты `src/web/server.ts` (`/api/meta`, `/api/tasks…`, `/api/teams…`, `/api/docs…`, `/api/images`, поток `/api/events`), поэтому SPA работает без переделки. Поток становится журналом событий с `Last-Event-ID`. Контракт описывается в OpenAPI, из него генерируются типы для SPA.
2. **Агенты: MCP + HTTP.** Все действия агента — инструменты MCP (Streamable HTTP) с прежними именами: `genie_task`, `team_send`, `team_status`, `team_spawn` и другие, `docs_search`, `docs_read`, `docs_note`. Каждый агент получает токен, привязанный к проекту, команде, имени и роли; права проверяет сервер. Это закрывает ограничение из [[architecture]]: сейчас роль задаётся переменной окружения, и агент с bash теоретически может её подменить.
3. **Почта агентам.** Сервер хранит письма и отдаёт их длинным опросом или SSE (`inbox?wait=…`). Семантика сохраняется: письмо забирается в момент доставки, уровни и дайджест работают как сейчас. Как письмо попадает в сессию, решает адаптер харнесса; для pi — так же, как сейчас (`sendUserMessage`, steer для `high`).
4. **События.** У каждого типа события — версионированная JSON-схема, одна и та же для SSE, автоматизаций и исходящих webhooks.

## Данные

- Одна БД сервера в каталоге данных: проекты, пользователи, задачи (с колонкой проекта), команды, почта, журнал, автоматизации, каналы. Раз инсталляция одна на команду, отдельный файл на проект не нужен, а сквозные экраны («Мои задачи», «Ждут меня») становятся простыми запросами.
- Индекс знаний — отдельный файл-кэш, который можно удалить и перестроить, как сейчас.
- Содержимое артефактов пока остаётся в БД; если объёмы вырастут — вынос в файловое хранилище по хешу.
- Импорт: `genie project import <repo>` поднимает существующий `.genie/genie.db` (схема 3) в проект сервера с сохранением ID, истории, команд и почты.

## Перенос по шагам

Принцип — постепенная замена: TS-версия остаётся рабочей, пока Go-сервер не догонит её по возможностям; новые возможности на TS не пишутся, только исправления.

1. Каркас: Go-модуль, `genie serve`, каталог данных, миграции, встроенная SPA, сборка и тесты в CI.
2. Трекер: модель, стейт-машина, права, DoR/DoD, эпики, артефакты, история — сразу с журналом событий. Сначала переносятся тесты (`test/tracker.test.ts`, `test/render.test.ts`), потом код.
3. REST API для SPA и SSE на журнале; импорт `.genie/genie.db`. Экраны задач, эпиков и доски работают на Go-сервере.
4. CLI с паритетом команд трекера.
5. Команды и почта: запуск pi-участников, пульс, восстановление, почта с уровнями и дайджестом, ручное управление командами; спецификация — `test/mail-delivery.test.ts`.
6. Агентский контракт (MCP + HTTP), расширение pi как тонкий клиент, серверный оркестратор.
7. Docs-ядро: парсер, индекс, ссылки, L0/L1-контекст, impact (спецификация — `test/docs*.test.ts`, `test/web-*.test.ts`, `test/cli-docs.test.ts`); сначала над `docs/` репозитория, затем корень переезжает в vault ([[platform/knowledge-vault]]).
8. Переключение ежедневной работы на Go-сервер, когда e2e-сценарии `scripts/e2e*.ts` проходят на нём; удаление TS-ядра (`src/tracker`, `src/team`, `src/docs`, `src/web`, `src/cli`).

## Подключение агентов — отдельная тема

Владелец решил проработать это отдельно. Два направления стоит развести:

- **Агент как клиент.** Человек работает в своём агенте (pi, Claude Code, Codex, opencode…) и через MCP с личным токеном заводит задачи, смотрит статус, отвечает на вопросы команд, берёт «пульт» оркестратора.
- **Агент как исполнитель.** genie запускает участника команды не только в pi, но и в другом харнессе — через адаптер `AgentRuntime`.

Что фиксируем уже сейчас, чтобы не закрыть дорогу:

- все операции агента существуют как инструменты MCP;
- личность агента — токен, а не переменные окружения;
- доставка почты отделена от харнесса.

Вопросы к отдельному обсуждению:

1. Какие харнессы в приоритете?
2. Могут ли «чужие» агенты быть полноправными участниками команды (принимать письма посреди работы) или только выполнять разовые задания?
3. Как передавать промпт роли, модель и уровень thinking в харнессы со своей конфигурацией?
4. Изоляция и доступ к файлам.
5. Авторизация личных агентов: токены или OAuth для MCP.
